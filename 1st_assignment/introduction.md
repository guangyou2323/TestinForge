## 3. Background Concepts

### 3.1 What machine learning actually is

Traditional programming: **a human writes the rules**, the program applies them.

```
rules + data  ──►  [ program ]  ──►  answers
```

Machine learning: **the program learns the rules from examples**.

```
data + answers ──►  [ learning algorithm ]  ──►  model (the learned rules)
                                                     │
new data ────────────────────────────────────────────┴──► predicted answer
```

So a **model** is just a set of learned numbers (parameters) that maps input features to an output. "Training" means searching for the numbers that make the model's predictions match the known answers as closely as possible.

### 3.2 The main branches

| Branch | Training data contains answers? | Typical task | Example |
|---|---|---|---|
| **Supervised** | Yes (labelled) | Predict a known output | Spam / not spam |
| **Unsupervised** | No | Find structure | Group customers into segments |
| **Reinforcement** | Feedback via reward | Learn a policy | Game-playing agents |

**This module covers supervised learning only.**

### 3.3 Classification vs regression

Both are supervised, and both predict a target — the difference is the *type* of target:

| | Target type | Example question | Example algorithm |
|---|---|---|---|
| **Classification** | A **category / class** | "Is this tumour malignant or benign?" | Logistic Regression, Decision Tree, Random Forest, k-NN, SVM |
| **Regression** | A **number** | "What will this house sell for?" | Linear Regression, Ridge, Gradient Boosting Regressor |

Terminology you will see everywhere:

- **Features** — the input columns, usually written `X`. Shape: `(n_samples, n_features)`.
- **Target / label** — the answer column, usually written `y`. Shape: `(n_samples,)`.
- **Sample / instance / row** — one observation.
- **Class** — one possible value of a classification target (e.g. `setosa`).

**Binary classification** has 2 classes; **multiclass** has 3 or more. scikit-learn handles both with the same API.

### 3.4 The scikit-learn API — everything is an estimator

This is the single most important thing to internalise. Almost every object in scikit-learn follows the same three methods:

```python
model = SomeClassifier(...)   # 1. choose an algorithm + hyperparameters
model.fit(X_train, y_train)   # 2. LEARN from the training data
y_pred = model.predict(X_test)  # 3. PREDICT on unseen data
```

Some also provide:

- `predict_proba(X)` → probability per class, e.g. `[[0.9, 0.1]]`
- `transform(X)` / `fit_transform(X)` → used by preprocessors (scalers, encoders)
- `score(X, y)` → a default quality metric (accuracy for classifiers)

Because the API is uniform, you can swap `LogisticRegression()` for `RandomForestClassifier()` and change **nothing else**. That is what makes scikit-learn so effective for learning and for rapid comparison.

Two vocabulary words that beginners mix up:

- **Parameters** — learned from data by `fit()` (e.g. the coefficients).
- **Hyperparameters** — set *by you* before `fit()` (e.g. `n_estimators=100`, `max_depth=5`). Tuning these is "hyperparameter tuning".

## 4. The Standard Workflow

```
1. Load the data                 ← sklearn.datasets or a CSV file
2. Explore it                    ← shapes, class balance, missing values, ranges
3. Split: train / test           ← NEVER evaluate on the data you trained on
4. Build a Pipeline              ← scaling/encoding + classifier, as one object
5. Train (fit) on the train set
6. Evaluate on the test set      ← accuracy, precision, recall, F1, confusion matrix
7. Tune hyperparameters          ← cross-validation on the TRAIN set only
8. Inspect & interpret           ← which features mattered?
9. Save the model and re-use it  ← joblib.dump / joblib.load
```

Steps 3–6 are non-negotiable. Step 4 is what keeps you honest.

### 4.1 Why split into train and test?

If you train on all your data and then measure accuracy on that same data, you are marking your own exam. A model can memorise the training rows (**overfitting**) and score 100% while being useless on new data.

| Set | Typical share | Purpose |
|---|---|---|
| **Training set** | 70–80% | The model learns from this |
| **Test set** | 20–30% | A final, one-time, honest estimate of real-world performance |

Use `train_test_split(..., stratify=y, random_state=42)` so that:

- `stratify=y` keeps the class proportions identical in both sets (critical for imbalanced data), and
- `random_state=42` makes your result **reproducible** — every groupmate gets the same numbers.

The test set is sacred: look at it once, at the end. If you tune settings by peeking at test scores, the test set silently becomes a training set and your reported accuracy becomes fiction.

### 4.2 Why cross-validation?

A single train/test split is noisy: you might get lucky (or unlucky) with the split. **k-fold cross-validation** splits the training data into `k` parts (folds), trains `k` times — each time holding out a different fold — and averages the scores.

```
Fold 1: [val][   ][   ][   ][   ]
Fold 2: [   ][val][   ][   ][   ]
Fold 3: [   ][   ][val][   ][   ]
Fold 4: [   ][   ][   ][val][   ]
Fold 5: [   ][   ][   ][   ][val]    →  mean score ± std
```

`cross_val_score(model, X_train, y_train, cv=5)` is the workhorse. A mean of `0.96 ± 0.02` is a far more trustworthy statement than a single `0.97`.

**Rule of thumb:** cross-validate to *choose* between models and hyperparameters; use the test set only to *report* the final number.

### 4.3 Pipelines prevent data leakage

Some algorithms (Logistic Regression, SVM, k-NN) require features on a comparable scale. **Data leakage** means information from the test set sneaks into training — for example, computing the mean and standard deviation on the *whole* dataset before splitting, then scaling with them. Your score looks great and reality disappoints you.

A `Pipeline` removes the temptation entirely:

```python
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression

model = Pipeline([
    ("scaler", StandardScaler()),
    ("clf", LogisticRegression(max_iter=1000)),
])
model.fit(X_train, y_train)   # scaler statistics come from X_train ONLY
```

Inside a pipeline, every step is fitted on the training part only — during cross-validation the scaler is re-fitted per fold, which is exactly correct.

> Tree-based models (Decision Tree, Random Forest) do **not** need feature scaling; distance- and gradient-based models do. Including the scaler anyway is harmless and keeps your code uniform.

## 6. Evaluating a Classifier

### 6.1 The confusion matrix — the source of all the other metrics

For binary classification, with "positive" = the class you care about:

|  | Predicted negative | Predicted positive |
|---|---|---|
| **Actual negative** | TN (true negative) | FP (false positive) — *false alarm* |
| **Actual positive** | FN (false negative) — *missed case* | TP (true positive) |

Everything else is derived from these four numbers:

| Metric | Formula | Answers the question |
|---|---|---|
| **Accuracy** | `(TP + TN) / total` | "How often is the model right overall?" |
| **Precision** | `TP / (TP + FP)` | "When it says positive, how often is it right?" |
| **Recall** (sensitivity) | `TP / (TP + FN)` | "Of the real positives, how many did it catch?" |
| **F1-score** | harmonic mean of precision & recall | "One balanced number when both matter" |

For multiclass problems, scikit-learn computes these **per class** and then averages them. Read the `macro avg` row (every class weighted equally) and the `weighted avg` row (weighted by class size) in `classification_report`.

### 6.2 Why accuracy is often the wrong headline number

Imagine a disease that affects 1 in 100 people, and a lazy model that always answers "healthy".

- Accuracy: **99%** — sounds excellent.
- Recall for the disease class: **0%** — it never finds a single patient.

This is why the **class balance matters**. Always check it (`Counter(y)`), and prefer `classification_report` over bare accuracy on imbalanced problems.

### 6.3 Which metric should I optimise?

| Situation | Prefer | Reason |
|---|---|---|
| Balanced classes (e.g. Iris) | Accuracy or F1 | No class is more important |
| Imbalanced, false positives costly | **Precision** | e.g. flagging legitimate email as spam |
| Imbalanced, false negatives costly | **Recall** | e.g. missing a cancer diagnosis |
| Both costs matter | **F1** | Single balanced summary |

### 6.4 Overfitting vs underfitting

| | Training score | Test score | Meaning | Remedy |
|---|---|---|---|---|
| **Underfitting** (too simple) | low | low | Model missed the pattern | More/better features, a more flexible model |
| **Good fit** | high | high (close to train) | Generalises well | — |
| **Overfitting** (too complex) | very high | much lower | Model memorised noise | Less complexity, more data, regularisation |

Always compare train and test scores. A large gap is the fingerprint of overfitting. A `DecisionTreeClassifier` with unlimited depth will typically score ~100% on training data — and noticeably less on test data. Limiting `max_depth` closes that gap. This experiment is one of your tasks.

## 8. Using Your Own Dataset Instead

The workflow is identical; only steps 1–2 change.

```python
import pandas as pd
from sklearn.model_selection import train_test_split

df = pd.read_csv("data/my_data.csv")
print(df.head())
print(df["target"].value_counts())      # class balance
print(df.isna().sum())                  # missing values

X = df.drop(columns=["target"])         # features
y = df["target"]                        # labels
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42
)
```

Three extra things to handle with real data:

1. **Missing values** — use `SimpleImputer(strategy="median")` as the *first* step of your pipeline.
2. **Categorical features** — use `OneHotEncoder(handle_unknown="ignore")`, combined with numeric preprocessing via `ColumnTransformer`.
3. **Uneven classes** — check `value_counts()`; consider `class_weight="balanced"` and judge with F1/recall rather than accuracy.

A good next dataset to try: the **Titanic** survival dataset or the **Breast Cancer Wisconsin** dataset (`load_breast_cancer`, also built in — binary classification, 30 features, and a genuinely useful real-world problem).

## 11. Glossary

| Term | Meaning |
|---|---|
| **Feature** | An input variable used for prediction |
| **Target / label** | The value being predicted |
| **Estimator** | Any scikit-learn model object with `fit`/`predict` |
| **Hyperparameter** | A setting you choose before training |
| **Parameter** | A value the model learns during training |
| **Pipeline** | A chain of preprocessing + model treated as one estimator |
| **Cross-validation** | Averaging scores over k train/validation splits |
| **Overfitting** | Memorising training data; poor generalisation |
| **Underfitting** | Too simple to capture the pattern |
| **Data leakage** | Test information contaminating training, inflating scores |
| **Stratified split** | A split preserving class proportions |
| **Baseline** | A trivial model used as a sanity-check reference |
| **Confusion matrix** | Table of predicted vs actual class counts |
